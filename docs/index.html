Step 1 of 6 — Connect

Log into your AOS8 Mobility Master and (optionally, for later steps) Aruba Central. Everything below runs through your local proxy agent — if you haven't started it yet, do that first.

Get the proxy agent running

The proxy agent is what actually talks to your controller, Central, and APs — this web page can't reach them directly. It runs locally, on a machine with network access to your equipment.

  1. Download it: Download proxy agent (.zip) Just the proxy agent folder — not the whole project.
  2. Unzip it — you'll get a proxy-agent folder.
  3. Double-click start_proxy_agent.command (Mac) or start_proxy_agent.bat (Windows).
  4. Look for its icon in your menu bar (Mac) or system tray (Windows) — that confirms it's running. Click the icon any time to reopen this GUI, or to turn on Debug mode.

First run installs a few Python packages automatically — that can take a minute. Nothing to type.

Aruba Central * for licensing checks, verification & site assignment

How do I get these values?
  1. In Central, set the filter to Global, then go to Maintain → Organization → Platform Integration → Rest API.
  2. Open the My Apps & Tokens tab and click + Add Apps & Token to create an application — this gives you the Client ID and Client secret.
  3. Select that application and click Generate to create a token, then Download Token to get the Access token and Refresh token.
  4. The API Gateway base URL is shown on the same API Gateway page — it's region-specific (e.g. apigw-uswest4.central.arubanetworks.com).

Access tokens expire after 2 hours; the refresh token is valid 14 days and lets the proxy agent refresh automatically — worth filling in even though it's optional.

Step 3 of 6 — Pre-flight checks

        
Confirm the selected APs are actually ready to convert before you reboot them. Selected APs: 0.

      


      

        ⚠
        

          Configuration that won't carry over automatically. Per HPE's "Configuration retained or migrated" guide: the AP's native/management VLAN is never retained (it always assumes VLAN 1 on the uplink after conversion). AP1X, HTTP proxy, PPPoE, and mesh settings stay on the AP but are not migrated into Central — a mismatch here can make the AP flap and auto-restore. Configure these in the target Central AP group before converting if your APs use them.
        

      


      

        ⚠
        

          Country code is permanent. ap convert writes this controller's configured regulatory domain (country code) onto every AP it converts — once written it cannot be changed without a factory reset, and it also permanently ties FCC-locked hardware to a US-only regulatory domain. If the APs you're converting are destined for a Central site in a different country than this controller, stop and re-home them from a controller in the correct region first.

          Watch for auto-join into a nearby cluster. A converted AP can automatically join an existing Instant/AOS10 cluster within radio range and inherit that cluster's configuration — which can look like a failed migration when the AP is actually fine, just in the wrong place. If a converted AP doesn't land where you expected, check for other clusters nearby before assuming something went wrong. (source)
        

      


      

        
3a. AP hardware compatibility

        
Not every AP model supports ap convert (older AP-200 series can't run past InstantOS 6.5; some AP-325 units lack enough memory). This checks your current selection against a best-known, deliberately incomplete compatibility list — "unknown" means verify manually, not "safe."

        
        

      


      

        
3b. Controller firmware version

        
ap convert was introduced in ArubaOS 8.6.0.0 — on older firmware the command doesn't exist and conversion fails confusingly. Checks the anchor controller(s) for your currently-selected APs (loads topology automatically if you haven't already).

Where the AOS10 image comes from during conversion. 3c. AP → Central network reachability (approximate)

        
A very common real-world failure isn't the conversion itself — it's a converted AP that never appears in Central because its VLAN can't reach Aruba's cloud services at all (DNS, outbound HTTPS, firewall/proxy rules). This checks from the proxy agent's own network, which is a useful signal but not a guarantee if the AP's VLAN has a different egress path than the proxy agent's — the real confirmation is the Verify step after conversion. Also confirm manually: the AP's VLAN needs working DNS and NTP (a badly-skewed clock can break the TLS handshake to Central), neither of which can be tested from here.

Step 4 of 6 — Execute conversion

        
This reboots the selected APs into AOS10. They'll reconnect through Activate and check in with Central under the group pre-validate reported in Step 3. A selection spanning multiple Mobility Controllers is automatically split into one action per MD, using each AP's own anchor controller.

Clear a stale conversion job

        
If you navigated away instead of letting a batch finish (or cancelling it), a job can be left outstanding on the controller. This tool never uses all-aps mode — Execute always targets specific APs — but a leftover job is still worth clearing explicitly rather than leaving it. Clears ap convert state for the controller(s) anchoring your currently selected APs; this is controller-wide, not limited to those specific APs.
